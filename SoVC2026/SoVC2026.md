# 첫 번째 축: DevOps

AI와 협업하기 위한 인프라

---

## DevOps 없는 바이브 코딩의 현실

- "AI가 코드를 짜줬는데, **어떻게 배포하지?**"
- "로컬에서는 되는데 **서버에서 안 돼요**"
- "AI한테 시켰더니 **main에 직접 push** 했어요"
- 수동 배포. 환경 불일치. 롤백 불가.

> 결과: AI가 빨리 짜면 짤수록, 빨리 망가진다.

---

## 왜 DevOps가 바이브 코딩의 전제조건인가

- AI는 빠르게 코드를 생성한다
  - 배포/검증 파이프라인이 없으면 그 속도가 **독**이 된다
- 바이브 코딩의 핵심은 "빠른 반복"
  - CI/CD 없이는 반복이 느려진다
- 삼양식품 사례에서도 **자동배포 환경**이 세 가지 전제조건 중 하나였다

---

## 개인 개발자를 위한 DevOps 최소 셋업

4가지만 하면 된다:

1. **Git 브랜치 전략**: main 보호, feature branch → PR → merge
2. **CI 파이프라인**: GitHub Actions로 lint + test + build 자동화
3. **CD 파이프라인**: 자동 배포 (Vercel, Railway, AWS 등)
4. **환경 분리**: dev / prod 최소 2단계

---

<!-- _class: impact -->

## 이 셋업도 AI에게 시키면 된다

---

## AI에게 DevOps 셋업 시키기

- "이 프로젝트에 **GitHub Actions CI/CD**를 설정해줘"
- "**Dockerfile**을 만들어줘. Python 3.12, uv 사용"
- "PR merge 시 **자동 배포**되게 workflow 추가해줘"

CLAUDE.md에 배포 환경 정보를 기록해두면 AI가 참조한다.

> 근데 AI가 만든 CI 설정이 맞는지는 어떻게 알지?
> → 그래서 **이해**가 필요하다. (4막에서 이어짐)

---

## DevOps와 AI의 시너지

```
AI가 코드를 짠다
  → CI가 자동으로 검증한다
    → 실패하면 AI가 CI 로그를 보고 수정한다
      → 다시 push → 자동 검증
        → 성공하면 CD가 자동 배포한다
```

인간은 **PR을 리뷰**하고, 나머지는 자동화.

---

## AI 시대의 DevOps 모범사례

- <span class="accent">커밋을 자주, 작게</span> — AI 코딩은 평소보다 잦은 커밋이 필요
- <span class="accent">PR 단위를 작게 유지</span> — AI가 만든 큰 변경은 리뷰가 어렵다
- <span class="warn">환경변수와 시크릿 관리</span> — AI가 실수로 하드코딩하는 것 방지
- <span class="accent">Dockerfile을 프로젝트에 포함</span> — 환경 재현성
- <span class="accent">모니터링/알림 설정</span> — 배포 후 문제를 빠르게 감지

---

<!-- _class: impact -->

## 최소 셋업을 넘어서:
## IaC가 가져오는 인프라의 자유

---

## Infrastructure as Code — 왜 지금인가

예전에는 IaC가 **전문 인프라 엔지니어의 영역**이었다.

- Terraform, CDK, Pulumi — 러닝커브가 높았다
- "인프라는 인프라팀이 해주는 거 아닌가요?"

바이브 코딩 시대에 달라진 것:

- AI에게 "이 서비스를 AWS에 배포할 Terraform 코드를 짜줘"
- AI에게 "이 아키텍처를 CDK로 구현해줘"
- <span class="accent">인프라 코드도 바이브 코딩의 대상이 된다</span>

---

## IaC + 바이브 코딩 = 인프라의 민주화

| 과거 | 현재 (IaC + AI) |
|------|----------------|
| 서버 설정은 인프라팀에 요청 | AI에게 Terraform 코드 요청 |
| 콘솔 클릭으로 수동 구성 | 코드로 선언, 버전 관리 |
| 환경마다 미묘하게 다름 | 동일 코드 = 동일 환경 보장 |
| 롤백이 무섭다 | `git revert` 한 번이면 롤백 |
| 인프라 변경에 며칠 대기 | PR → 머지 → 자동 반영 |

> 개발자 개인이 프로덕션급 인프라를 직접 구축할 수 있는 시대.

---

## 최신 기술의 민주화: 바이브 코딩이 장벽을 낮춘다

예전에는 **전문가만 쓸 수 있던 기술**들:

- **Kubernetes** — "YAML 지옥"이라 불리던 것을 AI가 생성
- **서버리스 아키텍처** — Lambda, API Gateway 설정을 자연어로
- **데이터 파이프라인** — Airflow DAG, Spark job을 AI와 함께 구축
- **보안 설정** — IAM 정책, 네트워크 ACL을 AI에게 검토 요청
- **모니터링** — Grafana 대시보드, 알림 규칙을 AI가 작성

> <span class="accent">AI가 최신 기술의 "번역기" 역할을 한다.</span>
> 개념만 이해하면, 구현은 AI와 함께.

---

## DevOps 전체 셋업: 개인이 가질 수 있는 풀스택

```
소스코드 (Git)
  → CI (GitHub Actions: lint, test, build, security scan)
    → 컨테이너 빌드 (Docker)
      → IaC로 인프라 프로비저닝 (Terraform/CDK)
        → CD (자동 배포)
          → 모니터링 + 알림 (Grafana/CloudWatch)
            → 장애 감지 → AI가 분석 → 수정 PR 생성
```

이 전체를 **한 사람이 AI와 함께 구축하고 운영**할 수 있다.

> 예전에는 이게 팀 6명의 일이었다.
> 지금은 AI와 함께하는 1명의 일이 될 수 있다.

---

## 근데 그걸 다 혼자 하면 위험하지 않나?

- <span class="warn">맞다. 혼자 하면 위험하다.</span>
- 그래서 **자동화된 안전장치**가 필요하다:
  - CI에서 보안 스캔 자동 실행
  - IaC 변경에 `plan` 단계 필수 (적용 전 미리보기)
  - 비용 알림 설정 (AI가 비싼 인스턴스를 띄울 수 있다)
  - PR 리뷰 없이 인프라 변경 금지

> DevOps의 핵심은 "자동화"가 아니라 **"안전한 자동화"**다.

# 두 번째 축: 테스트 자동화

AI 코드의 안전망

---

## 테스트 없는 바이브 코딩의 현실

- "AI가 짠 코드가 맞는지 **어떻게 알아?**"
- "고치라고 했더니 **다른 곳이 깨졌어요**" (회귀 버그)
- "테스트 실패하니까 AI가 **테스트를 삭제**했어요"

---

<!-- _class: impact -->

## AI의 이상한 트릭

테스트를 실패한다고?
그럼 그 테스트를 **없애면** 되겠군!

점수가 낫다고?
기준점을 **낮추면** 되겠군!

---

## 왜 테스트가 바이브 코딩 시대에 더 중요해졌나

- AI가 코드를 짜는 시대 → 인간이 코드를 **한 줄씩 읽는 건 비현실적**
- 테스트는 "AI가 올바르게 작동하는지 **자동으로 검증**하는 장치"
- 테스트코드가 코드베이스에 포함되어 **가드레일** 역할
  - AI가 이상한 곳으로 가는 것을 막아준다

> AI 시대에 와서 오히려 테스트코드가 중요해지는 듯.
> 우리가 직접 안 짜도 된다는 점이 더욱 좋다.

---

## TDD는 끝났나? 아니, 진화했다.

| 방식 | 테스트 작성 | 코드 작성 |
|------|-----------|----------|
| 전통적 TDD | 사람 | 사람 |
| AI 시대 레벨 1 | AI | AI |
| AI 시대 레벨 2 | **사람** | AI |
| AI 시대 레벨 3 | AI (사람이 리뷰) | AI |

> 레벨 2가 가장 안전하고 효과적. 테스트가 곧 명세(spec)다.

---

## 레벨 1: AI에게 테스트도 같이 만들라고 하기

- "이 기능을 구현하고, **테스트코드도 함께 작성**해줘"
- CLAUDE.md / cursor rule에 명시:

```
모든 새 기능에는 반드시 단위 테스트를 포함하세요.
```

> 가장 쉽다. 하지만 테스트 품질을 보장하기 어렵다.

---

## 레벨 2: 사람이 테스트를 먼저, AI가 코드를 작성

- 테스트가 **명세(spec)** 역할을 함
- AI에게: "이 테스트를 통과하는 코드를 작성해줘"
- 테스트는 내가 원하는 동작의 **계약서**

> <span class="accent">가장 안전하고 효과적인 방법.</span>
> 내가 원하는 것을 테스트로 표현하고, AI가 구현한다.

---

## 레벨 3: AI가 둘 다 작성, 사람이 테스트를 리뷰

- AI가 코드와 테스트를 모두 작성
- 사람은 **테스트의 품질**을 검증
  - "이 테스트가 충분한가?"
  - "엣지 케이스가 빠지지 않았나?"

> 코드 전체를 읽는 것보다 테스트만 리뷰하는 게 훨씬 빠르다.

---

## CLAUDE.md에 꼭 넣어야 할 테스트 규칙

```markdown
## 테스트 정책
- 기존 테스트를 삭제하거나 수정하지 마세요
- 새 기능에는 반드시 단위 테스트를 포함하세요
- 테스트 실패 시 테스트가 아닌 코드를 수정하세요
- 테스트 커버리지를 낮추는 변경은 하지 마세요
- 절대 API 이름과 파라미터는 바꾸지 마세요
```

> <span class="warn">LLM은 "하지말라"보다 "하라"를 잘 듣는 경향이 있다.</span>
> '금지 + 바른 방향'을 함께 기술하자.

---

## 테스트 자동화 실전 팁

- CI에 테스트를 **필수로 걸기** (PR merge 조건)
- 커버리지 리포트 자동 생성
- AI에게 "이 코드의 **엣지 케이스를 5개** 찾아서 테스트해줘"
- 통합 테스트 + E2E 테스트도 AI에게 맡기기 (Playwright 등)
- 테스트 실패 시 AI에게 **CI 로그를 보여주고** 수정 요청

---

## 근데 AI가 짠 테스트를 신뢰할 수 있나?

- 사람이 짠 테스트도 완벽하지 않다
- 핵심은 "자동화된 검증 루프가 **있느냐 없느냐**"
- 테스트가 있으면 최소한 **회귀를 잡을 수 있다**

> 테스트 없음 vs 불완전한 테스트 → 불완전해도 있는 게 압도적으로 낫다.

# AI가 다 해주면 우리는 뭘 배워야 하나?

---

## 학습이 여전히 중요한 이유

- P = X × Y + Z 에서 **X(개발자 역량)가 여전히 가장 큰 변수**
- AI의 출력을 **평가**하려면 기본 역량이 필요
- AI가 못하는 것:
  - 비즈니스 맥락 이해
  - 아키텍처 판단
  - 가치 선택(Trade-off)

> AI가 선택지를 만들어줄 수 있다.
> <span class="accent">선택은 우리가 현명하게 해야 한다.</span>

---

## 가브리엘 피터슨의 AI Driven Study

> OpenAI 연구원. 고등학교 중퇴 후 독학으로 개발자가 됨.

**핵심 원리 6가지**
1. **현실 문제에서 시작**한다 (bottom-up이 아닌 problem-first)
2. **재귀적 갭 메우기**: 만든다 → 막힌다 → 묻는다 → 다시 만든다
3. **아하 모먼트**를 자주 만들도록 프롬프트를 최적화
4. 질문이 떠오르는 순간 **즉시 AI에 던진다**
5. **결과물(데모)**이 신뢰와 기회를 만든다
6. **사람 피드백 + AI 피드백**을 둘 다 활용한다

---

## 핵심 엔진: 재귀적 갭 메우기

```
만들어본다 → 막힌다 → 왜 막혔는지 묻는다 → 설명을 듣는다 → 다시 만든다
```

갭은 2종류:
- **개념 갭**: 이해가 안 됨 → "이게 뭔지 설명해줘"
- **실행 갭**: 구현이 안 됨 → "이걸 어떻게 하는지 보여줘"

> 둘 다 같은 루프로 처리한다. AI가 24시간 대기 중이다.

---

## AI Driven Study 운영 체계

세 가지 탭을 항상 켜두기:

| 탭 | 용도 |
|----|------|
| **Learn** | 개념, 직관, 요약 |
| **Build** | 코드/설계/시안 생성, 디버깅 |
| **Review** | 피드백, 리팩토링, 개선 아이디어 |

그리고 하루 100개의 **"작은 질문"**을 허용하기.

## DevOps와 테스트를 AI로 학습하기

DevOps를 모르는데 어떻게 시작하지?

- AI에게 물어보면 된다:
  "이 Python 프로젝트에 GitHub Actions CI를 설정하고 싶어. **단계별로 알려줘**"
- 단, <span class="warn">이해를 포기하지 말 것</span> — 재귀적 갭 메우기 적용

테스트를 안 짜봤는데?

- AI에게 기존 코드의 테스트를 만들게 한 뒤, 그 테스트를 **읽으며 학습**
- "이 테스트가 뭘 검증하는지 **한 줄로 설명**해줘"

## 이해를 잃지 않는 체크리스트

- [ ] 나는 이걸 **한 문장**으로 설명할 수 있나?
- [ ] 내가 이해한 흐름을 **단계별**로 말할 수 있나?
- [ ] **엣지 케이스 3개**를 떠올릴 수 있나?
- [ ] 다른 사람에게 **5분 안에 데모**할 수 있나?
- [ ] AI가 틀릴 때 어떻게 **검증**할 건가?

> 이 체크리스트를 통과 못하면, AI가 일한 거지 내가 일한 게 아니다.

---

## 흔한 실패 패턴 5가지

1. AI가 준 답을 그대로 붙여넣고 **이해를 포기** → 갭 메우기 루프
2. 질문이 **추상적**이라 결과도 추상적 → 구체적 맥락 제공
3. 디버깅 자료가 **부족** → 에러 로그 + 환경 + 기대 동작 세트
4. 완벽한 공부를 하느라 **데모가 없음** → "작동하는 최소 버전" 우선
5. **피드백 회피** → 데모 데이, 공개 약속으로 압박 만들기

> 해결은 모두 **루프 강화**로 귀결된다.

# 세 축의 연결과 미래

---

## 세 축이 만드는 선순환

```
AI 기반 학습으로 역량 향상 (X↑)
  → DevOps + 테스트로 프로세스 최적화 (Y↑)
    → AI 활용도 증가 (Z 효과 극대화)
      → 더 복잡한 문제를 풀 수 있게 됨
        → 다시 학습이 필요 → 루프 반복
```

> 한 축만 강해서는 안 된다. 세 축이 함께 돌아야 한다.

---

## 이것만으로 충분한가?

"테스트와 DevOps를 갖추면 AI 코딩이 안전한가?"
- 완벽하지 않다. 하지만 **없는 것보다 압도적으로 낫다.**

"AI로 학습하면 정말 깊은 이해가 가능한가?"
- 핵심은 "이해를 포기하지 않는 습관"
- <span class="warn">도구가 아니라 태도의 문제다.</span>

---

## 심지어 더 느리게 만들었다는 연구도 존재한다

- METR 연구: 오픈소스 개발자가 AI 도구를 사용했을 때 **19% 더 느려짐**
- 하지만 여기엔 반전이 있다:
  - 투입된 개발자들 중 AI 도구를 오래 써본 사람은 **소수**
  - 업무 방식 자체를 AI 친화적으로 재편하지 않았음
  - <span class="accent">이미 AI에 친화적인 사람은 효율 향상을 경험</span>

> 답은 도구가 아니라 **방식의 전환**에 있다.

## 미래 전망

- **2025**: 바이브 코딩 "되냐 안되냐" 논쟁

- **2027~**: AI 에이전트가 독립적으로 더 긴 작업 수행

> 2029년 안에 인간이 1달 걸리는 작업을 할 수 있다고 함.
