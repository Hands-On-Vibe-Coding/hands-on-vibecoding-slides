# State of Vibe Coding 2026 — Ideation

> 바이브 코딩 시대, 개발자 개인의 역량을 극대화하는 세 가지 축:
> DevOps, 테스트 자동화, AI 기반 학습

## 개요

- SoVC2025에서 "바이브 코딩이란 무엇인가"와 "조직은 어떻게 도입하나"를 다뤘다면,
  SoVC2026은 **개인 개발자가 바이브 코딩 시대에 어떻게 자신의 역량을 극대화할 것인가**에 집중한다.
- 세 가지 축을 중심으로 전개:
  1. DevOps — AI와 협업하기 위한 인프라이자 안전망
  2. 테스트 자동화 — AI가 짠 코드를 신뢰할 수 있게 만드는 핵심 장치
  3. AI 기반 효율적 학습 — 개인의 기술적 깊이를 극대화하는 엔진

## 네러티브 구조

하용호 스타일("AI로 개발을 가속하기") 네러티브 패턴을 따른다:
- 잘못된 사례로 공감 → 질문형 브릿지 → 증거 동반 해법 → 양면 검토 후 판단
- 전체 흐름: 실용(팁) → 거시(왜 이게 중요한가) → 철학(개발자의 미래)

## 1막: 바이브 코딩 2026 — 무엇이 달라졌나 (도입부)

### 1-1. 오프닝: 작년과 올해의 차이

- 안티패턴 먼저: "작년에 바이브 코딩 도입했다가 실패한 사람?"
  - 코드는 나오는데 유지보수가 안 된다
  - 테스트 없이 AI가 짠 코드를 프로덕션에 올렸다가 장애
  - 혼자 빠르게 만들었는데, 팀에서 아무도 이해 못하는 코드
- 질문 브릿지: "왜 바이브 코딩이 약속한 생산성이 안 나올까?"

### 1-2. 바이브 코딩의 생산성 공식 (복습 + 확장)

- P = X * Y + Z (SoVC2025에서 소개한 공식)
  - X: 개발자의 역량 → **이번 발표의 핵심. 학습으로 극대화**
  - Y: 도구와 프로세스 → **DevOps + 테스트 자동화가 여기에 해당**
  - Z: AI 단독 생산성 → 꾸준히 증가 중이지만 여전히 한계
- 핵심 메시지: "X와 Y를 키우지 않으면 Z만으로는 한계가 있다"

### 1-3. 세 가지 축 소개

- DevOps, 테스트 자동화, AI 기반 학습이 왜 서로 연결되는가
- 비유: "DevOps는 도로, 테스트는 가드레일, 학습은 운전 실력"
  - 도로 없이는 달릴 수 없고
  - 가드레일 없이는 추락하고
  - 운전 실력 없이는 아무리 좋은 차도 소용없다

## 2막: DevOps — AI와 협업하기 위한 인프라 (첫 번째 축)

### 2-1. 안티패턴: DevOps 없는 바이브 코딩

- "AI가 코드를 짜줬는데, 어떻게 배포하지?"
- "로컬에서는 되는데 서버에서 안 돼요"
- "AI한테 시켰더니 main에 직접 push 했어요"
- 잘못된 사례: 수동 배포, 환경 불일치, 롤백 불가

### 2-2. 왜 DevOps가 바이브 코딩의 전제조건인가

- AI는 빠르게 코드를 생성한다 → 배포/검증 파이프라인이 없으면 그 속도가 독이 된다
- 바이브 코딩의 핵심은 "빠른 반복" → CI/CD 없이는 반복이 느려진다
- 삼양식품 사례 복습: 자동배포 환경이 세 가지 전제조건 중 하나였음

### 2-3. 개인 개발자를 위한 DevOps 최소 셋업

- 개인도 할 수 있는 최소한의 DevOps:
  1. **Git 브랜치 전략**: main 보호, feature branch → PR → merge
  2. **CI 파이프라인**: GitHub Actions로 lint + test + build 자동화
  3. **CD 파이프라인**: 자동 배포 (Vercel, Railway, AWS 등)
  4. **환경 분리**: dev / staging / prod 최소 2단계
- AI에게 DevOps 셋업도 시킬 수 있다
  - "이 프로젝트에 GitHub Actions CI/CD를 설정해줘"
  - CLAUDE.md에 배포 환경 정보를 기록해두면 AI가 참조

### 2-4. DevOps와 AI의 시너지

- AI가 코드를 짜고 → CI가 자동으로 검증하고 → CD가 자동으로 배포
- 실패하면 AI가 CI 로그를 보고 수정 → 다시 push → 자동 검증
- "인간은 PR을 리뷰하고, 나머지는 자동화"
- Claude Code의 `/fix-github-issue` 같은 워크플로우가 DevOps 위에서 동작

### 2-5. 팁: AI 시대의 DevOps 모범사례

- 커밋을 자주, 작게 (AI 코딩은 평소보다 잦은 커밋이 필요)
- PR 단위를 작게 유지 (AI가 만든 큰 변경은 리뷰가 어렵다)
- 환경변수와 시크릿 관리 (AI가 실수로 하드코딩하는 것 방지)
- Dockerfile/docker-compose를 프로젝트에 포함 (환경 재현성)
- 모니터링/알림 설정 (배포 후 문제를 빠르게 감지)

## 3막: 테스트 자동화 — AI 코드의 안전망 (두 번째 축)

### 3-1. 안티패턴: 테스트 없는 바이브 코딩

- "AI가 짠 코드가 맞는지 어떻게 알아?"
- "고치라고 했더니 다른 곳이 깨졌어요" (회귀 버그)
- "테스트 실패하니까 AI가 테스트를 삭제했어요"
- 하용호 PDF 인용: "AI의 이상한 트릭 — 테스트 실패? 그럼 그 테스트를 없애면 되겠군!"

### 3-2. 왜 테스트가 바이브 코딩 시대에 더 중요해졌나

- AI가 코드를 짜는 시대 → 인간이 코드를 한 줄씩 읽는 건 비현실적
- 테스트는 "AI가 올바르게 작동하는지 자동으로 검증하는 장치"
- 테스트코드가 코드베이스에 포함되어 가드레일이 되어줌
  - AI가 이상한 곳으로 가는 것을 막아준다
- TDD vs AI 시대의 테스트:
  - 전통적 TDD: 사람이 테스트 → 사람이 코드
  - AI 시대: 사람이 테스트 → AI가 코드 (또는 AI가 둘 다, 사람이 검증)

### 3-3. AI와 함께하는 테스트 전략

- **레벨 1: AI에게 테스트도 같이 만들라고 하기**
  - "이 기능을 구현하고, 테스트코드도 함께 작성해줘"
  - CLAUDE.md / cursor rule에 "모든 기능에 테스트를 포함할 것" 명시
- **레벨 2: 사람이 테스트를 먼저 작성하고, AI가 코드를 작성**
  - 테스트가 명세(spec) 역할을 함
  - AI에게 "이 테스트를 통과하는 코드를 작성해줘"
  - 가장 안전하고 효과적인 방법
- **레벨 3: AI가 테스트와 코드를 모두 작성, 사람이 테스트를 리뷰**
  - 테스트의 품질을 사람이 검증
  - "이 테스트가 충분한가? 엣지 케이스가 빠지지 않았나?"

### 3-4. CLAUDE.md에 테스트 관련 규칙 넣기

- 하용호 PDF 인용: "절대 테스트 코드는 건들지마", "절대 API 이름과 파라미터는 바꾸지마"
- 테스트코드 변경가능 여부를 명시하는 것이 중요
  - 테스트가 잘 확립되면 → 제한을 풀고 리팩토링도 맡길 수 있음
- 구체적인 규칙 예시:
  ```
  - 기존 테스트를 삭제하거나 수정하지 마세요
  - 새 기능에는 반드시 단위 테스트를 포함하세요
  - 테스트 실패 시 테스트가 아닌 코드를 수정하세요
  - 테스트 커버리지를 낮추는 변경은 하지 마세요
  ```

### 3-5. 테스트 자동화 실전 팁

- CI에 테스트를 필수로 걸기 (PR merge 조건)
- 커버리지 리포트 자동 생성
- AI에게 "이 코드의 엣지 케이스를 5개 찾아서 테스트해줘" 요청
- 통합 테스트 + E2E 테스트도 AI에게 맡기기 (Playwright 등)
- 테스트 실패 시 AI에게 CI 로그를 보여주고 수정 요청

### 3-6. 양면 검토

- "테스트를 AI가 짜면 테스트 자체를 신뢰할 수 있나?"
  - 사람이 짠 테스트도 완벽하지 않다
  - 핵심은 "자동화된 검증 루프가 있느냐 없느냐"
  - 테스트가 있으면 최소한 회귀를 잡을 수 있다
- 비용 대비 효과: 테스트 작성 시간 vs 장애 대응 시간

## 4막: AI 기반 효율적 학습 — 개인 역량 극대화 (세 번째 축)

### 4-1. 질문 브릿지: "AI가 다 해주면 우리는 뭘 배워야 하나?"

- 바이브 코딩 시대에도 학습이 중요한 이유:
  - P = X * Y + Z 에서 X(개발자 역량)가 여전히 가장 큰 변수
  - AI의 출력을 평가하려면 기본 역량이 필요
  - AI가 못하는 것: 비즈니스 맥락 이해, 아키텍처 판단, 가치 선택

### 4-2. 가브리엘 피터슨의 AI Driven Study (핵심 요약)

- 출처: OpenAI 연구원, 고등학교 중퇴 후 독학으로 개발자가 됨
- 핵심 원리:
  1. 현실 문제에서 시작한다 (bottom-up이 아닌 problem-first)
  2. 재귀적 갭 메우기: 만든다 → 막힌다 → 묻는다 → 다시 만든다
  3. 아하 모먼트를 자주 만들도록 프롬프트를 최적화한다
  4. 질문이 떠오르는 순간 즉시 AI에 던진다
  5. 결과물(데모)이 신뢰와 기회를 만든다
  6. 사람 피드백 + AI 피드백을 둘 다 활용한다
- Learn / Build / Review 세 탭 항시 운영

### 4-3. DevOps와 테스트를 AI로 학습하기 (실전 적용)

- "DevOps를 모르는데 어떻게 시작하지?"
  - AI에게 물어보면 된다: "이 Python 프로젝트에 GitHub Actions CI를 설정하고 싶어. 단계별로 알려줘"
  - 단, 이해를 포기하지 말 것 — 재귀적 갭 메우기 적용
- "테스트를 안 짜봤는데?"
  - AI에게 기존 코드의 테스트를 만들게 한 뒤, 그 테스트를 읽으며 학습
  - "이 테스트가 뭘 검증하는지 한 줄로 설명해줘"
- 핵심: AI를 "대신 하는 도구"가 아니라 "함께 배우는 동료"로 사용

### 4-4. 학습과 실무를 분리하지 않는 방법

- 7일 스프린트 (AI Driven Study):
  | Day | 활동 |
  |-----|------|
  | 1 | 현실 문제 하나 선정 |
  | 2 | AI와 함께 최소 데모 구현 (테스트 포함) |
  | 3 | CI/CD 파이프라인 설정 (AI에게 시키며 학습) |
  | 4 | 실패 수집 + 갭 메우기 |
  | 5 | 피드백 데이 (동료 리뷰 + AI 리뷰) |
  | 6 | 개선 실험 (성능, UX, 테스트 보강) |
  | 7 | 산출물 정리 + 배포 |

### 4-5. 이해를 잃지 않는 체크리스트

- 나는 이걸 한 문장으로 설명할 수 있나?
- 내가 이해한 흐름을 단계별로 말할 수 있나?
- 엣지 케이스 3개를 떠올릴 수 있나?
- 다른 사람에게 5분 안에 데모할 수 있나?
- AI가 틀릴 때 어떻게 검증할 건가?

### 4-6. 흔한 실패 패턴과 대응

1. AI가 준 답을 그대로 붙여넣고 이해를 포기 → 갭 메우기 루프
2. 질문이 추상적이라 결과도 추상적 → 구체적 맥락 제공
3. 디버깅 자료 부족 → 에러 로그 + 환경 + 기대 동작 세트로 제공
4. 완벽한 공부를 하느라 데모가 없음 → "작동하는 최소 버전" 우선
5. 피드백 회피 → 데모 데이, 공개 약속으로 압박 만들기

## 5막: 종합 — 세 축의 연결과 미래 (마무리)

### 5-1. 세 축이 만드는 선순환

```
AI 기반 학습으로 역량 향상 (X↑)
  → DevOps + 테스트로 프로세스 최적화 (Y↑)
    → AI 활용도 증가 (Z 효과 극대화)
      → 더 복잡한 문제를 풀 수 있게 됨
        → 다시 학습이 필요 → 루프 반복
```

### 5-2. 양면 검토: 이것만으로 충분한가?

- "테스트와 DevOps를 갖추면 AI 코딩이 안전한가?"
  - 완벽하지 않다. 하지만 없는 것보다 압도적으로 낫다.
- "AI로 학습하면 정말 깊은 이해가 가능한가?"
  - 연구 결과: AI 도구 사용 시 학습 효과에 대한 양면적 결과
  - 핵심은 "이해를 포기하지 않는 습관" — 도구가 아니라 태도의 문제
- METR 논문 인용: AI 능력은 7개월마다 2배씩 성장 중
  - 하지만 성공률을 높이려면 작업 사이즈를 AI가 운영할 수 있는 크기로 줄여야

### 5-3. 미래 전망

- 2025: 바이브 코딩 "되냐 안되냐" 논쟁
- 2026: "어떻게 잘 하느냐" — DevOps, 테스트, 학습이 차별화 요소
- 2027~: AI 에이전트가 독립적으로 더 긴 작업 수행 → 인간은 "아키텍트 + 검증자 + 의사결정자"
- "AI가 선택지를 만들어줄 수 있다. 선택은 우리가 현명하게 해야 한다."

### 5-4. 오늘 바로 할 수 있는 3가지

1. 내 프로젝트에 CI/CD 파이프라인을 설정한다 (없다면 AI에게 시킨다)
2. 테스트가 없는 코드에 AI와 함께 테스트를 추가한다
3. 이번 주 "현실 문제 1개"를 골라 7일 스프린트를 시작한다

### 5-5. 클로징 메시지

- "도로(DevOps)를 깔고, 가드레일(테스트)을 세우고, 운전 실력(학습)을 키워라"
- "옳고 그름이 아니라, 옳음과 옳음 사이의 선택 — Trade Off 사이의 가치의 선택자가 되어라"
