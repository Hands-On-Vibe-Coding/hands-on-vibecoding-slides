# 바이브 코딩

---

## 바이브 코딩 - 2025년 현황

- 바이브 코딩이 되냐 안되냐를 논쟁하는 시점은 지났음
- 어떻게 도입할 것인가, 얼마나 빨리 도입할 것인가가 관건
  ```
  "국내 동종업계에 성공사례가 있나요?"
  "그걸 보는 순간 님 비즈니스는 시한부 선고를 받은겁니다."
  ```
- IT가 모든 비즈니스의 핵심에 자리하고 있는 현대사회에서 바이브 코딩의 도입이 늦어지면 늦어질수록 경쟁에서 뒤쳐질 수 밖에 없음

---

## 글로벌 Vibe Coding 도입 현황

- 2028년까지 엔터프라이즈 개발자의 약 90%가 AI 코드 어시스턴트를 사용(Gartner 전망).
- 2025년 초 조사에서 조직의 61%가 에이전틱(Agentic) AI 개발을 시작했다고 보고.
- GitHub Copilot: 전 세계 약 77,000개 기업 도입, 수십만 개발자 사용. 엔터프라이즈 보안/프라이버시 옵션 강화로 표준화 진행.
- 생태계 경쟁: GitHub(MS), Anthropic, OpenAI, Amazon, Google, GitLab, Cognition 등 14+ 벤더가 IDE 통합·긴 문맥·보안/컴플라이언스로 기업 시장 공략.


## 바이브 코딩의 본질

- 바이브 코딩은 코딩만이 아님. 소프트웨어 개발 전반에 걸친 **AI 협업 프로세스**.
- 기본적으로 바이브 코딩은 기존 개발프로세스와 동일함. 다만 작업 주체가 사람에서 AI로 바뀌는 것 뿐.
- 따라서 기본 소프트웨어 개발 역량이 없이는 제대로 사용하기 어려움

> 바이브 코딩은 기존 개발 프로세스와 모범사례와 안티패턴을 공유한다.

---

## 바이브 코딩의 생산성

```latex
P = X * Y + Z
```

- P: 생산성
- X: 개발자의 생산성
- Y: 도구와 프로세스의 생산성
- Z: AI가 단독으로 낼 수 있는 생산성

> 1. 현 시점의 바이브 코딩은 개발자의 능력에 크게 의존한다
> 2. 올바른 도구와 프로세스의 활용이 생산성을 극대화한다
> 3. AI가 단독으로 내는 생산성은 제한적이지만 꾸준히 증가하고 있다

## 삼양식품 사례: 개요

> 식품회사가 5개월 만에 AI 서비스를 미국에 론칭하다

- **팀 구성**: PM 1명, 디자이너 1명, 엔지니어 1명 (총 3명)
- **프로젝트**: Popow.ai - 틱톡 트렌드 분석 및 바이럴 영상 분석 서비스
- **성과**: 5개월 만에 미국 시장 론칭
- **효율성**: "2주 걸리는 기능이 하루 만에 완성"

---

## 삼양식품 사례: 초기 도입 전략

> 세 가지 전제 조건으로 시작

1. **리포지토리 중심 정보관리**
   - 모든 프로젝트 정보를 외부가 아닌 저장소 내에 기록
   - AI가 언제든 참조할 수 있는 구조

2. **AI 기반 질의응답**
   - "현재 구현 상태가 어떻게 되나?" → AI에게 즉시 질문
   - 컨텍스트 스위칭 비용 최소화

3. **자동배포 환경**
   - Slack-Cursor 연동
   - 메시지 하나로 개발 서버 반영

---

## 삼양식품 사례: 스케일업의 벽

> 프로젝트가 커지면서 직면한 문제

- **AI의 환각(Hallucination)**: 잘못된 코드 생성 증가
- **컨텍스트 과부하**: Claude.md 규칙 파일이 2,000줄 돌파
- **의도 상실**: 전체 컨텍스트의 30%를 규칙이 차지

```
규칙이 많아질수록 AI는 더 혼란스러워졌다
```

> 현재는 Claude Skills가 등장하여 컨텍스트를 목적별로 잘게 쪼개어 관리하는것이 가능해짐

## 가프리엘 피터슨은 누구?

## 왜 학습인가?

- 소프트웨어 개발은 본질적으로 가설수립과 실험을 반복하는 과학 탐구의 과정과 동일함
- 모든 개발자는 학습의 전문가가 되어야 한다
- 어떻게 효과적을 학습할 것인가?

## AI Driven Study란?

> AI를 "대신 해주는 도구"가 아니라 "내 머리를 확장하는 학습 동반자"로 쓰는 방식

- **목표**: 더 빨리 이해하고, 더 빨리 만들어서, 더 빨리 혁신한다
- **결과**: 학습과 실행이 분리되지 않는다 (학습 = 구현 과정)

**핵심 원리 6가지**
1. 현실 문제에서 시작하면 학습이 쉬워진다
2. top-down 학습은 "재귀적 갭 메우기"다
3. 아하 모먼트를 자주 만들도록 프롬프트를 최적화한다
4. 질문이 떠오르는 순간 즉시 AI에 던진다
5. 결과물(데모)이 신뢰와 기회를 만든다
6. 사람 피드백 + AI 피드백을 둘 다 활용한다

---

## 왜 기존 학습이 느렸나

| 기존 방식 | AI 방식 |
|----------|---------|
| 기초 → 응용의 선형 경로 | 문제를 즉시 주고받고 |
| 실제 압박이 없으면 집중 흐려짐 | 압박을 인위적으로 만들고 |
| 피드백이 느리고 드물다 | 피드백을 24/7로 만든다 |

**핵심 엔진: 재귀적 갭 메우기**
```
만들어본다 → 막힌다 → 왜 막혔는지 묻는다 → 설명을 듣는다 → 다시 만든다
```

## 역할별 적용: 기획자(PM/PO)

> 더 빨리 도메인 지식을 흡수하고, 더 빨리 검증 가능한 가설을 만든다

**AI 사용 포인트**
- **문제 분해**: "이 문제를 5개의 하위 문제로 쪼개줘"
- **가설 생성**: "가설 10개, 반증 방법, 측정 지표까지"
- **리서치 요약**: "핵심 차이점만 비교표로"
- **실험 설계**: "A/B, 코호트, 이벤트 설계, 샘플 사이즈 근사"

---

## 역할별 적용: 개발자

> 모르는 영역도 빠르게 구현하고, 이해를 잃지 않는다

**AI 사용 포인트**
- **problem-first**: "이 기능을 구현하는 가장 작은 수직 슬라이스"
- **디버깅 동료**: "에러 로그 + 환경 + 기대 동작"
- **코드 리뷰**: "버그 가능성, 엣지 케이스, 성능 병목"
- **지식 압축**: "이 코드에서 핵심 원리 3개만 뽑아줘"

**Top-down 루프**: 작동하는 최소 버전 → 안 되는 지점 수집 → AI와 고침 → 한 줄로 설명할 수 있을 때까지

---

## 역할별 적용: 디자이너

> 트렌드/패턴을 더 빨리 흡수하고, 설계 의도를 더 명확히 만든다

**AI 사용 포인트**
- **패턴 학습**: "이 화면의 UI 패턴 이름과 사용 맥락"
- **논리화**: "이 레이아웃 선택의 장단점과 대안"
- **카피/마이크로카피**: "톤 가이드에 맞춰 10안"
- **접근성**: "WCAG 관점에서 체크리스트와 수정안"

## 7일 AI Driven Study 스프린트

| Day | 활동 |
|-----|------|
| 1 | 문제 하나를 고른다 (현업/사이드 상관없음) |

| 4 | 갭 메우기 1차 (개념+실행) |
| 5 | 피드백 데이 (사람 리뷰 + AI 리뷰) |
| 6 | 개선 실험 2개 (A/B 혹은 전/후 비교) |
| 7 | 공개 가능한 산출물로 정리 |

## 흔한 실패 패턴 5가지

1. AI가 준 답을 그대로 붙여 넣고 **이해를 포기**함
2. 질문이 **추상적**이라 결과도 추상적임
3. 디버깅 자료(로그/재현)가 **부족**함
4. "완벽한 공부"를 하느라 **데모가 없음**
5. 피드백 회피 (사람 리뷰를 **무서워함**)

> 해결은 모두 **루프 강화**로 귀결된다

## 권한: AI 도구 사용 권한 부여

> 개인이 실험할 수 있는 환경을 만들어야 한다

**필요한 권한**
- AI 도구 구독/사용 비용 지원 (Cursor, Claude, ChatGPT 등)
- 외부 API 호출 권한 (보안 가이드라인 내에서)
- 실험용 샌드박스 환경 제공
- 개인 학습 시간 보장 (20% 룰 등)

**주의사항**
- 승인 절차를 최소화 (속도가 생명)
- "안 된다"가 아닌 "이렇게 하면 된다" 가이드 제공
